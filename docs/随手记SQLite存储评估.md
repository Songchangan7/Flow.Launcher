# 随手记 SQLite 存储评估

> 评估日期：2026-06-25  
> 范围：Quick Note 插件（`Creta.Plugin.BrowserBookmark`）  
> 结论：**现阶段继续使用 JSON 文件存储，暂不迁移 SQLite。**

## 1. 当前方案

- 单文件 `notes.json`，结构为 `NoteItem` 数组
- 每次写入全量序列化并覆盖文件
- 已通过阶段 6 补齐导入/导出与 JSON 备份，数据可迁移

## 2. 继续使用 JSON 的理由

| 维度 | 说明 |
|------|------|
| 数据规模 | 随手记以短文本、个人轻量记录为主，绝大多数用户笔记量在数百～数千条 |
| 可维护性 | JSON 可直接打开、备份、合并，与现有导入导出能力一致 |
| 实现成本 | 无额外依赖，插件保持轻量，与 Creta 插件分发模型匹配 |
| 迁移风险 | 切换存储引擎需要数据迁移、回滚与兼容测试，收益尚未超过成本 |
| 阶段目标 | 阶段 6 强调「降低数据锁定风险」；JSON + 导入导出已满足备份与迁移诉求 |

## 3. SQLite 的潜在收益

- 单条增量更新，避免大文件反复重写
- 内置全文检索（FTS5），复杂筛选与排序更高效
- 更适合多字段索引（标签、来源、最近查看时间等）
- 为后续 AI 总结、跨笔记聚合查询提供查询层基础

## 4. 建议触发重新评估的条件

满足以下 **任意两条** 时，建议启动 SQLite 方案设计与 POC：

1. **规模**：单用户活跃笔记持续超过 **5,000** 条，或 `notes.json` 常态超过 **5 MB**
2. **性能**：保存/加载出现可感知延迟（如保存 > 500 ms，冷启动加载 > 1 s）
3. **检索**：需要在全库范围做高频全文检索、多条件组合查询，且现有内存过滤不够用
4. **功能**：计划落地依赖事务或多表关联的能力（版本历史、附件、笔记链接图等）
5. **并发**：存在多进程/多实例同时写入同一笔记库的需求

## 5. 若未来迁移的推荐路径

1. **Schema 对齐**：以当前 `NoteItem` 为单表主结构（含 `Source`、`LastViewedAt` 等扩展字段）
2. **双写或一次性迁移**：读取现有 `notes.json` → 写入 SQLite → 校验条数与抽样内容
3. **保留 JSON 导出**：迁移后仍提供 JSON 备份/导出，避免新的厂商锁定
4. **仓储抽象**：将 `NoteRepository` 读写细节与查询 API 分离，降低切换存储实现的影响面

## 6. 近期数据模型预留（已落地）

为后续能力铺路，已在 `NoteItem` 增加：

| 字段 | 用途 |
|------|------|
| `Source` | 记录创建来源（如 `launcher`、`editor`、`import-text`） |
| `LastViewedAt` | 最近查看时间（复制、打开编辑器等场景更新） |

旧版 `notes.json` 无上述字段时可正常加载，写入时按约定补全。

## 7. 结论

**维持 JSON 为默认存储**；把工程精力集中在录入体验、检索与管理能力上。当用户规模或功能复杂度达到第 4 节触发条件时，再投入 SQLite 迁移与 FTS 查询层建设。
